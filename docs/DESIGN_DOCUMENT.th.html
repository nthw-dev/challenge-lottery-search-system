02 บริบทและขอบเขต

พื้นที่ค้นหาจริงคือหนึ่งล้าน ไม่ใช่สิบล้าน

โจทย์คือ ค้นสลาก 6 หลักจำนวน 10,000,000 ใบ ด้วย pattern 6 ตัวอักษรที่มี wildcard * แล้วแจกจ่ายสลากที่เข้าเงื่อนไขให้ผู้ใช้ที่เข้ามาพร้อมกัน โดยต้องไม่มีสลากใบใดไปถึงผู้ใช้สองคน สิ่งที่ต้องส่งคือ solution architecture, storage สำหรับ production พร้อมเหตุผล, การวิเคราะห์ประสิทธิภาพ และกลยุทธ์ด้าน concurrency ที่ป้องกันการแจกซ้ำ หัวข้อ 4 ตอบทั้งสี่ข้อโดยตรง หัวข้อ 5 ถึง 8 ให้รายละเอียดและหลักฐาน

2.1  สมมติฐานตั้งต้น

สลาก 6 หลักมีค่าที่เป็นไปได้เพียง 10⁶ = 1,000,000 ค่า สลาก 10 ล้านใบจึงเฉลี่ยราว 10 ใบต่อหนึ่งเลข โจทย์จึงไม่ใช่ "ค้นข้อมูลสิบล้านแถว" แต่คือ "ตัดสินว่าเลขไหนบ้างในหนึ่งล้านเลขที่เข้าเงื่อนไข แล้วดึงสลากของเลขเหล่านั้น" พื้นที่ค้นหาแบบที่สองเล็กกว่าสิบเท่า มีขนาดคงที่ไม่ว่าจะมีสลากกี่ใบ และเล็กพอที่จะอยู่ใน cache ตลอดเวลา การตัดสินใจทุกข้อในเอกสารนี้สืบเนื่องจากจุดนี้

ขนาดของผลลัพธ์ต่างกันได้ถึงหก order of magnitudeตามจำนวน wildcard การรายงานประสิทธิภาพจึงแยกตามคลาส wildcard (หัวข้อ 6.2)

3.2  สิ่งที่ตั้งใจไม่ทำ

อยู่นอกขอบเขตโดยตั้งใจ เพื่อพิสูจน์ว่า database ตัวเดียวเพียงพอ ก่อนจะเพิ่มอะไรเข้าไป

  • Authentication และ authorization
  • Payment ระบบออกรางวัล และระบบงวด
  • การขยาย database แนวนอน replication และ read replica
  • Caching layer ทุกชนิด ตัด Redis ออกโดยตั้งใจ
  • Observability stack ระดับ production (Prometheus, Grafana, tracing)
  • CI/CD pipeline

04 สรุปการออกแบบ

โจทย์ 4 ข้อ การตัดสินใจ 4 ข้อ แต่ละข้อมีผลวัดรองรับ

คำตอบต่อสิ่งที่โจทย์ขอทั้งสี่ข้อ การตัดสินใจแต่ละข้อมีเหตุผลจากผลวัดบน proof of concept และขยายความในหัวข้อที่ระบุ

สิ่งที่โจทย์ขอการตัดสินใจเหตุผลรายละเอียด
Solution architecture, data structures, algorithms API ที่ไม่เก็บ state หนึ่งตัว หน้า PostgreSQL 17 หนึ่ง instance ซึ่งมีตาราง tickets (10M แถว) ตาราง numbers แบบคงที่ (10⁶ แถว หนึ่งแถวต่อค่าที่เป็นไปได้ มี index รายหลัก) และ ledger allocations แบบ append-only การค้นหาจะหาเลขที่เข้า pattern บน numbers ก่อน — หลักหน้าคงที่ → ช่วงบน primary key, ระบุครบ → point lookup, กรณีอื่น → B-tree รายหลัก — แล้ว join เข้า tickets ผ่าน partial index ของแถวที่ว่าง พื้นที่ค้นหาคือเลขที่เป็นไปได้ 10⁶ ค่า ไม่ใช่สลาก 10⁷ ใบ มีขนาดคงที่ไม่ว่าจะมีสลากกี่ใบ และอยู่ใน cache ได้ทั้งก้อน index รวม 201 MB ครึ่งหนึ่งของทางเลือกแบบรายหลัก หัวข้อ 5.1 ถึง 5.3
Database / storage สำหรับ production PostgreSQL 17 instance เดียว ไม่มี cache ไม่มี lock service ไม่มี search engine FOR UPDATE SKIP LOCKED เป็นเครื่องมือแจกงานที่ atomic และไม่มี deadlock ในตัว database เอง ข้อที่ยากที่สุดของโจทย์จึงไม่ต้องเพิ่ม component ใด การจองและการบันทึก audit อยู่ใน transaction เดียว partial index, expression index และ planner แบบคิดต้นทุนทำให้ index พื้นที่ 10⁶ ได้หลายแบบ มี component เดียวที่ต้องดูแล คาดการณ์ว่าใช้ 36 % ของ 6 core ที่เป้าตัวอย่าง 10,000 req/s หัวข้อ 6.1, 6.4
การวิเคราะห์ประสิทธิภาพ Strategy C: p95 46.7 ms ที่ 6,068 req/s บน pod 500m CPU ตัวเดียว แบนราบทุกคลาส wildcard เร็วกว่า LIKE สี่ order of magnitude ใน pattern ระบุครบ ทรัพยากรที่เต็มคือ API ที่ไม่เก็บ state ซึ่งขยายแนวนอนได้ trade-off ที่ยอมรับ: join เพิ่มหนึ่งชั้น (ต่ำกว่า 1 ms) ไม่มี ORDER BY ในการค้นหา และ latency ของการจองแย่ลงเมื่อ pattern ใกล้หมด วัดทั้งสี่กลยุทธ์บนข้อมูล 10M แถวชุดเดียวกัน C เป็นแบบเดียวที่ผ่านเกณฑ์ latency และเป็นแบบเดียวที่ย้ายคอขวดออกจาก database หัวข้อ 6.2, 7.1, 7.2
กลยุทธ์ concurrency / การแจกจ่ายสลาก SQL คำสั่งเดียว: CTE เลือกแถวด้วย FOR UPDATE SKIP LOCKED อัปเดตเป็นจองแล้ว และบันทึกลง ledger เลือกแถวด้วยการสุ่มเลขจริงใน pattern และ fall back ไปสแกน pattern เมื่อไม่พบ การจองหมดอายุด้วย TTL sweep แถวที่ถูกล็อกมองไม่เห็นจาก allocator อื่นจนกว่าจะ commit ไม่มี transaction ใดรอ และเกิด deadlock ไม่ได้ พิสูจน์ด้วยการจอง 342,412 ใบภายใต้ contention จากผู้ใช้ 200 คนบน pattern เดียว ซ้ำ 0 และ ledger ไม่ตรงกับสถานะ 0 หัวข้อ 5.4, 8.1

การออกแบบคือ API ที่ไม่เก็บ state หนึ่งตัว PostgreSQL 17 หนึ่ง instance และตารางสามตาราง ไม่มีอย่างอื่น ไม่มี cache ไม่มี lock service ไม่มี search engine ตัวเลขทุกตัวในเอกสารนี้วัดบน PostgreSQL 17.11 (หัวข้อ 6.4)

5.2  โครงสร้างข้อมูล

CREATE TABLE tickets (
  id          bigint    PRIMARY KEY,
  number      int       NOT NULL,            -- 0..999999
  status      smallint  NOT NULL DEFAULT 0,  -- 0=ว่าง, 1=จองแล้ว, 2=ขายแล้ว
  reserved_by int,
  reserved_at timestamptz
);

CREATE TABLE numbers (                       -- พื้นที่ค้นหา 1 ล้านแถว
  n  int PRIMARY KEY,                        -- 0..999999
  d1 smallint NOT NULL, d2 smallint NOT NULL, d3 smallint NOT NULL,
  d4 smallint NOT NULL, d5 smallint NOT NULL, d6 smallint NOT NULL
);

CREATE TABLE allocations (                   -- ledger แบบเขียนอย่างเดียว
  ticket_id bigint      NOT NULL,
  user_id   int         NOT NULL,
  at        timestamptz NOT NULL DEFAULT now()
);
การตัดสินใจเหตุผล
number เป็น int ไม่ใช่ char(6) ประหยัดราว 60 MB ที่ 10M rows เปรียบเทียบเร็วกว่า และดึงหลักด้วยเลขคณิตได้โดยไม่ต้องแปลง type การเติมศูนย์หน้าทำเมื่อส่งออก
ไม่เก็บหลักตัวเลขไว้บน tickets generated column หกคอลัมน์จะกิน heap เพิ่มราว 120 MB จึงย้ายไปไว้บนตาราง 1 ล้านแถวแทน ซึ่งต้นทุนต่ำกว่ามาก
status เป็น smallint เล็กและเปรียบเทียบเร็วกว่า enum หรือ text เพียงพอสำหรับสามสถานะ
แยกตาราง allocations ออกมา ทำให้การรับประกันว่าไม่แจกซ้ำตรวจสอบได้ด้วย query เดียว แทนที่จะต้องอนุมาน (หัวข้อ 5.4, 8.1)

numbers เป็นตารางคงที่ สร้างหนึ่งล้านแถวครั้งเดียวแล้วไม่เขียนอีก และเป็นเหตุผลที่ต้นทุนการค้นหาไม่โตตามจำนวนสลาก

5.3  อัลกอริทึมการค้นหาและ index

สำหรับ pattern อย่าง 1*3**6

  1. ตรวจ pattern แล้วแยกตำแหน่งที่เป็นตัวเลขคงที่กับ wildcard
  2. หาเลขที่เข้าเงื่อนไข บน numbers มีสองกรณีที่ยุบเป็นช่วงหรือจุดได้ คือหลักหน้าคงที่ติดกัน (123***) กลายเป็นช่วงบน primary key n BETWEEN 123000 AND 123999 และระบุครบทั้งหกหลัก (123456) กลายเป็น number = 123456 บน tickets โดยตรง กรณีอื่นใช้ B-tree ของแต่ละหลัก
  3. ดึงสลาก โดย join เลขเหล่านั้นเข้ากับ tickets(number) ผ่าน partial index ที่จำกัดไว้ที่ status = 0
  4. หยุดทันทีที่พอ โดยดัน LIMIT ลงไปถึงชั้น index scan
-- 123*** → อ่านเป็นช่วงบน primary key ของตาราง 1 ล้านแถว
SELECT id, number FROM tickets
WHERE status = 0
  AND number IN (SELECT n FROM numbers WHERE n BETWEEN 123000 AND 123999)
LIMIT 20;

-- ****23 → ใช้ index ของแต่ละหลักบนตาราง 1 ล้านแถว
SELECT id, number FROM tickets
WHERE status = 0
  AND number IN (SELECT n FROM numbers WHERE d5 = 2 AND d6 = 3)
LIMIT 20;

index ทั้งหมด 7 ตัว คือ index ของหกหลักบน numbers ขนาดราว 6.8 MB ต่อตัว บวกกับ partial B-tree บน tickets(number) รวม 201 MB ที่สลาก 10 ล้านใบ ส่วนที่อยู่บน numbers มีขนาดคงที่ มีเพียง index บนตารางสลากที่โตตามจำนวนสลาก และเพราะเป็น partial บน status = 0 index นี้จึงเล็กลงเมื่อสลากถูกขายไป

7.1  trade-off ด้านประสิทธิภาพที่ยอมรับ

  • join เพิ่มหนึ่งชั้น Strategy C อ่านสองตาราง ต้นทุนที่วัดได้คือเศษเสี้ยวของมิลลิวินาที เพราะตาราง numbers อยู่ใน cache
  • ตารางที่ต้อง seed เพิ่มหนึ่งตาราง คำสั่งเดียว รันครั้งเดียว
  • wildcard ที่อยู่หน้าไม่ได้ประโยชน์จาก prefix range ****23 fall back ไปใช้ index รายหลักที่ 0.13 ms จึงไม่ใช่เส้นทางที่อ่อนแอ
  • การจองช้าลงเมื่อสลากใกล้หมด เมื่อ ****23 ถูกจองไป 96 % ค่า p95 ขึ้นจาก 75 ms เป็น 510 ms เพราะการสุ่มเลขพบสลากที่ถูกจองแล้วบ่อยขึ้น การถอน pattern ที่สลากใกล้หมดเป็นการตัดสินใจระดับ product ไม่ใช่ปัญหาของ database แต่ต้องออกแบบเผื่อไว้

7.3  ความทนทานและการดูแลระบบ

liveness ต้องไม่ขึ้นกับ database เมื่อใช้ baseline strategy connection pool เต็มไปด้วย query ช้า readiness probe ตอบไม่ทัน Kubernetes ถอด pod ออกจาก Service และ 15,592 จาก 16,528 request ล้มเหลว ซึ่งเป็นพฤติกรรมที่ถูกต้อง แต่ถ้า liveness probe แตะ database ด้วย Kubernetes จะ restart pod ที่ยังดีอยู่ระหว่างที่ database ช้า และเปลี่ยน degradation ให้กลายเป็น outage /healthz จึงตรวจแค่ process ส่วน /readyz ping database บันทึกไว้เป็น ADR-006

resource limit ต้องไปถึง runtime process ของ Go อ่านจำนวน core ของเครื่อง ไม่ใช่โควตาของ cgroup จึงตั้ง GOMAXPROCS และ GOMEMLIMIT ให้ชัดเจน ถ้าไม่ตั้ง runtime จะสร้าง thread มากเกินจริงและถูก OOM kill ในที่สุด

ความเสถียร การรันต่อเนื่อง 10 นาทีแบบผสมทั้งค้นหา จอง และคืน ได้ 942,015 request ไม่มี error ไม่มี restart ไม่มี OOM kill และ memory ของ API สูงสุดเพียง 26 MiB จาก limit 128 MiB

7.4  Observability

สัญญาณที่ต้องมีใน production: query plan ผ่าน pg_stat_statements lock contention ผ่าน pg_locks และ pg_stat_activity CPU และ memory ของแต่ละ pod เทียบกับ limit และ CPU throttling ซึ่งกราฟ CPU เฉลี่ยมองไม่เห็น และเป็นกลไกที่ทำให้ Strategy A ล้มเหลว (หัวข้อ 6.2) observability stack เต็มรูปแบบเป็นสิ่งที่ตั้งใจไม่ทำ (หัวข้อ 3.2)

09 ความเสี่ยงและข้อจำกัด

สิ่งที่การออกแบบนี้ยังไม่ได้พิสูจน์

  • 10,000 req/s มาจากการคำนวณ ไม่ใช่การวัด อัตราสูงสุดที่วัดจริงคือ 4,000 req/s เป้าตัวอย่างจึงเป็นการลากเส้นตรงต่อไปอีก 2.5 เท่า ข้อมูลสี่จุดสนับสนุนว่าเป็นเส้นตรง แต่ไม่ได้พิสูจน์ว่าจะจริงต่อไป ก่อนขึ้น production ควรทดสอบจริงด้วย load generator บนเครื่องที่แยกจาก cluster
  • พฤติกรรมเมื่อสลากใกล้หมดยังเข้าใจเพียงบางส่วน latency ของการจองแย่ลงเมื่อ pattern ใกล้ขายหมด แต่ยังไม่ได้กำหนดว่าควรถอน pattern ออกจากการขายที่จุดไหน
  • การวัดทั้งหมดมาจาก node เดียว ซึ่ง API, database และload generatorใช้ CPU ชุดเดียวกัน throughput สัมบูรณ์บนเครื่องที่แยกกันจะต่างออกไป แต่การเปรียบเทียบระหว่างกลยุทธ์ ซึ่งเป็นฐานของข้อเสนอนี้ จะไม่เปลี่ยน
  • ยังไม่ได้ทดสอบ failure mode ไม่มีการวัดใดครอบคลุมกรณี pod หาย rolling update หรือ failover ของ database ซึ่งเป็นช่วงที่ capacity ลดลง จึงควรเผื่อ replica เพิ่มอีกอย่างน้อยหนึ่งตัวจากที่คำนวณได้
  • ยังไม่ได้ทดสอบเมื่อสลากถูกจองไปแล้วเป็นส่วนใหญ่ การวัดทั้งหมดเริ่มจากสลากที่ว่างทั้งหมด ถ้าสลากถูกขายไปแล้ว 80 % partial index จะเล็กลงแต่โอกาสที่การสุ่มเลขจะพบสลากว่างก็ลดลง ทั้งสองผลต้องวัดจริง
  • สิ่งที่ตั้งใจไม่รวมไว้ authentication, payment, ระบบงวด, replication และ caching layer (หัวข้อ 3.2)

B.  คำศัพท์

คำศัพท์ความหมายในเอกสารนี้
p95เวลาที่ 95 % ของ request เร็วกว่าค่านี้ ใช้แทนค่าเฉลี่ยเพราะค่าเฉลี่ยซ่อนหางช้าที่ผู้ใช้รู้สึกได้จริง
VUvirtual user คือผู้ใช้จำลองหนึ่งคนใน load generator ที่ส่ง request วนซ้ำ 200 VUs คือจำลอง 200 คนพร้อมกัน
คลาส wildcardการจัดกลุ่ม pattern ตามจำนวน * (w0, w3, w4, w5) ต้องรายงาน latency แยกตามคลาส เพราะขนาดผลลัพธ์ต่างกันถึงหก order of magnitude
SKIP LOCKEDตัวเลือกของ SELECT … FOR UPDATE ที่สั่งให้ transaction ข้ามแถวที่ transaction อื่นถืออยู่ แทนที่จะรอ เป็นฐานของการรับประกันว่าไม่แจกซ้ำ
BitmapAndวิธีที่ planner รวมผลจากหลาย index จะคุ้มก็ต่อเมื่อแต่ละ index คัดแถวทิ้งได้มาก index ของเลขหลักเดียวคัดได้แค่ 10 % จึงเป็นเหตุที่ Strategy A ล้มเหลว
partial indexindex ที่จำกัดด้วยเงื่อนไข WHERE ในที่นี้คือ WHERE status = 0 จึงครอบคลุมเฉพาะสลากที่ว่าง และเล็กลงเมื่อสลากถูกขายไป
working setmemory ที่ใช้จริงโดยไม่นับ page cache ที่ระบบเรียกคืนได้ ตัวเลข memory ดิบของ container PostgreSQL จะอยู่ใกล้ 100 % ของ limit ตลอด เพราะ PostgreSQL ใช้พื้นที่ว่างเป็น page cache working set คือตัวเลขที่มีความหมาย
CPU throttlingเวลาที่ container ถูกปฏิเสธ CPU เพราะใช้เกินโควตา มองไม่เห็นในกราฟ CPU เฉลี่ย ต้องวัดตรงจาก cgroup
liveness / readinessliveness ถามว่า process ยังมีชีวิตไหม ถ้าไม่ผ่านจะถูก restart ส่วน readiness ถามว่ารับงานได้ไหม ถ้าไม่ผ่านจะถูกถอดจาก load balancer โดยไม่ restart
