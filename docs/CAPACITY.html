Capacity Planning · Sizing for 10,000 TPS

10K TPS Capacity Plan

ต้องใช้ pod และ resource เท่าไรถึงจะรับ 10,000 requests/วินาที โดยที่ทั้ง API และ database ใช้ทรัพยากรไม่เกิน 60 % ของ limit คำตอบมาจากการวัดจริงแบบขั้นบันไดที่ 1,000 ถึง 4,000 TPS แล้วคำนวณต่อ ไม่ใช่การเดา ทั้งเป้า 10,000 TPS และเพดาน 60 % เป็นค่าตัวอย่างที่ผู้เขียนกำหนดขึ้นเองเพื่อสาธิตวิธีคิด capacity ไม่ได้มาจากโจทย์ วิธีเดียวกันใช้กับเป้าอื่นได้โดยไม่ต้องเปลี่ยนอะไร

02 วิธีหาคำตอบ

วัดที่อัตราต่ำ แล้วคำนวณขึ้นไป ดีกว่ายิง 10,000 TPS จริง

ถ้ายิง 10,000 TPS จากเครื่องเดียวกับที่รัน cluster อยู่ ตัว k6 เองจะกิน CPU หลาย core ไปแย่งกับ pod ที่เรากำลังวัด ตัวเลขที่ได้จะไม่ใช่ต้นทุนจริงของระบบ แต่เป็นต้นทุนของระบบที่ถูกแย่ง CPU วิธีที่ให้คำตอบแม่นกว่าคือ

  1. ยิงเป็นขั้นบันไดที่อัตราซึ่งเครื่องรับไหวสบายๆ คือ 1,000 → 2,000 → 3,000 → 4,000 TPS ขั้นละ 60 วินาที
  2. วัด CPU ที่ใช้จริงในแต่ละขั้น แล้วดูว่าต้นทุนต่อ 1 TPS คงที่หรือไม่
  3. ถ้าคงที่ แปลว่าความสัมพันธ์เป็นเส้นตรง จึงลากเส้นต่อไปที่ 10,000 TPS ได้อย่างมีเหตุผล
  4. ตรวจว่าค่าที่คำนวณได้ยังอยู่ใต้เพดาน 60 % และตรวจข้อจำกัดอื่นที่ CPU ไม่ครอบคลุมด้วย
จุดสำคัญของการออกแบบ test

ใช้ executor แบบ ramping-arrival-rate ไม่ใช่การกำหนดจำนวน VU เพราะ VU ไม่ใช่ TPS ถ้ากำหนด VU แล้วระบบช้าลง TPS จะลดตามเองโดยที่เราไม่รู้ตัว แต่ arrival rate คือการบังคับอัตราคำขอต่อวินาทีโดยตรง ถ้าระบบตามไม่ทัน k6 จะรายงาน dropped_iterations ให้เห็นชัดเจน ในรอบนี้ยิงไป 579,999 ครั้ง จากที่ควรได้ 580,000 คิดเป็น 100.00 % แปลว่าอัตราที่ตั้งไว้เกิดขึ้นจริงเกือบสมบูรณ์

ส่วนผสมของ traffic ตั้งไว้ที่ 90 % เป็นการค้นหา และ 10 % เป็นการจองแล้วคืน การคืนของทันทีทำให้ของในระบบไม่หมด จึงวัดต้นทุนในสภาวะปกติ ไม่ใช่สภาวะของใกล้หมด

04 โมเดลและการคำนวณ

แยกงานพื้นหลังออกจากต้นทุนต่อ request

ถ้าเอา CPU ทั้งหมดหารด้วย TPS ตรงๆ จะได้ตัวเลขที่ลดลงเรื่อยๆ ตามโหลดที่เพิ่ม เพราะมีงานพื้นหลังที่คงที่ปนอยู่ ต้องแยกสองส่วนนี้ออกจากกันก่อน โดยลากเส้นตรงผ่านจุดที่ต่ำสุดกับสูงสุด

CPU ที่ใช้  =  งานพื้นหลัง  +  ต้นทุนต่อ request x TPS

API   =    -5m  +  0.1049 m/TPS      ที่ 10,000 TPS  ->  1,044m
DB    =  112m  +  0.2075 m/TPS      ที่ 10,000 TPS  ->  2,187m

ตรวจเพดาน 60 %
  API   1,044m / (4 pods x 500m)  =  52.2 %   ผ่าน
  DB    2,187m / 6,000m           =  36.5 %   ผ่าน

limit ขั้นต่ำที่ยังผ่านเพดาน
  API   1,044m / 0.60 = 1,740m  ->  ต้องมีอย่างน้อย 4 pods x 500m = 2,000m
  DB    2,187m / 0.60 = 3,645m  ->  ต้องมีอย่างน้อย 4,000m (จะได้ 54.7 % ซึ่งชิดเพดานเกินไป)

ค่าตัดแกนของ API ติดลบเล็กน้อย (-5m) เป็นผลข้างเคียงของการลากเส้นผ่านสองจุด ความหมายจริงคือ API แทบไม่มีงานพื้นหลังเลย ต้นทุนเกือบทั้งหมดแปรตามจำนวน request

ทำไม API ถึงเป็นตัวที่ชิดเพดานมากกว่า ทั้งที่ database มักเป็นคอขวดในระบบทั่วไป คำตอบอยู่ในรายงานผลทดสอบชุดก่อน คือ Strategy C ย้ายงานหนักออกจาก database ไปแล้ว งานที่เหลือของ database ต่อหนึ่ง request คือการอ่าน index ไม่กี่ครั้ง ส่วน API ต้องทำงาน HTTP, JSON และ connection pool ซึ่งกลายเป็นส่วนที่แพงกว่า

05 ข้อจำกัดอื่น

สามอย่างที่โมเดล CPU ไม่ครอบคลุม

1. Memory ของ database ไม่ได้โตเป็นเส้นตรง

ถ้าใช้วิธีลากเส้นตรงกับ memory จะได้คำตอบที่ผิด เพราะ memory ของ Postgres ไม่ได้โตตามจำนวน request แต่โตตามปริมาณข้อมูลที่ถูกดึงเข้า cache ซึ่งจะอิ่มตัวเมื่อข้อมูลร้อนถูก cache ครบแล้ว ดูจากส่วนต่างของแต่ละขั้นจะเห็นว่ามันลดลงเรื่อยๆ

2. Connection pool

จำนวน connection ที่ต้องใช้พร้อมกันคำนวณจาก TPS คูณเวลาที่ใช้ต่อ request ไม่ได้ขึ้นกับจำนวนผู้ใช้

เวลาเฉลี่ยฝั่ง server  =  0.69 ms
ที่ 10,000 TPS  ->  10,000 x 0.00069  =  6.9 connection ที่ต้องใช้พร้อมกัน
ที่มีอยู่       ->  4 pods x pgxpool 10  =  40 connection      เหลือเฟือ
max_connections ของ Postgres ตั้งไว้ 100

3. ขนาดของ node

รวม limit ทั้งหมดของ config ที่เสนอคือ CPU 8,000m และ memory 3,584Mi ในการวัดครั้งนี้ทำบน docker-desktop ที่มี 14 cores แต่มี memory ให้ Kubernetes ใช้ได้เพียง 3.73GiB จึงต้องบีบ database ลงเหลือ 2,560Mi ตอนทดสอบ ซึ่งยังผ่านเพดานที่ 51.7 % บน production ควรใช้ 3Gi ตามที่เสนอ เพื่อให้มีระยะห่างจากเพดานมากกว่านี้

 ตัวเลขจากสูตรเดียวกัน ยังไม่ได้วัดจริง ใช้เป็นแนวทางวางแผนเท่านั้น

ฝั่ง API ขยายง่ายเพราะไม่มี state เพิ่ม pod แล้วได้ throughput เพิ่มตามสัดส่วน ส่วนฝั่ง database จะไปชนเพดานของเครื่องเดียวก่อน จุดนั้นค่อยพิจารณา read replica สำหรับ /v1/search ซึ่งเป็น read อย่างเดียว โดยให้ /v1/allocate ยังยิงเข้า primary เท่านั้น เพราะ SKIP LOCKED ต้องการความถูกต้องระดับ transaction

อย่าเพิ่ง scale up API pod

การเพิ่ม CPU ให้ API pod เดียวจาก 500m เป็น 1000m จะแทบไม่ช่วยอะไร เพราะตั้ง GOMAXPROCS=1 ไว้ Go จะใช้ได้แค่ thread เดียวอยู่ดี ถ้าจะขยายแนวตั้งต้องเพิ่ม GOMAXPROCS ตามด้วย แต่การเพิ่มจำนวน pod ง่ายกว่า และได้ความทนทานเพิ่มจากการมีหลาย instance ด้วย

07 ตอบโจทย์

เชื่อมกลับไปที่คำถามทั้ง 4 ข้อ

คำถามจากโจทย์คำตอบ
ใช้ database อะไร PostgreSQL ตัวเดียว 6 cores / 3Gi รับ 10,000 TPS ได้ที่ 36 % ของ limit ไม่ต้องมี Redis ไม่ต้องมี distributed lock และไม่ต้อง replication
algorithm และ index Strategy C คือค้นเลขที่เข้า pattern จากตาราง 1 ล้านแถวก่อน โดยแปลงหลักหน้าที่ล็อกไว้เป็นช่วงบน primary key แล้ว join เข้าตารางสลาก ทำให้ต้นทุนฝั่ง database เหลือเพียง 0.22 m-core ต่อ 1 TPS

รองรับ 10M+ และโหลดสูง ต้นทุนการค้นหาไม่ขึ้นกับจำนวนสลาก และต้นทุนต่อ TPS เป็นเส้นตรง จึงวางแผนขยายได้ด้วยสูตร ที่ 10,000 TPS ใช้ API 4 pods กับ Postgres 1 ตัว โดยทั้งคู่อยู่ใต้เพดาน 60 %

08 ข้อควรระวัง

สิ่งที่ตัวเลขชุดนี้ยังไม่ได้พิสูจน์

  • 10,000 TPS มาจากการคำนวณ ไม่ได้ยิงจริง ค่าที่วัดสูงสุดคือ 4,000 TPS การลากเส้นต่อไปอีก 2.5 เท่าตั้งอยู่บนสมมติฐานว่ายังเป็นเส้นตรงอยู่ ซึ่งข้อมูล 4 จุดที่มีสนับสนุนสมมติฐานนี้ แต่ไม่ได้พิสูจน์ว่าจะจริงตลอดไป ก่อนขึ้น production ควรยิงจริงจากเครื่องแยกที่ไม่ใช่เครื่องเดียวกับ cluster
  • ยังไม่ได้ทดสอบสภาวะของใกล้หมด รอบนี้คืนของทันทีทุกครั้ง ในของจริงถ้า pattern ยอดนิยมถูกจองไปเกือบหมด ต้นทุนต่อ request จะสูงขึ้นมาก ตามที่เห็นในรายงานชุดก่อนที่ latency ขึ้นจาก 75 ms เป็น 510 ms
  • ทุกอย่างรันบน node เดียว ทั้ง API, database และตัวยิงโหลดแย่ง CPU ชุดเดียวกัน บน production ที่แยกเครื่องกัน ตัวเลขน่าจะดีกว่านี้
  • ไม่ได้ทดสอบตอน pod ล่มหรือ rolling update ซึ่งเป็นสภาวะที่ capacity ลดลงชั่วคราว ควรเผื่อ pod เพิ่มอีกอย่างน้อย 1 ตัวถ้าต้องการรองรับการอัปเดตแบบไม่มี downtime
