# ADR-005: No `ORDER BY` on search

Status: Accepted · Date: 2026-09-05 · Relates to: design doc Section 5.3

## Context

The original search query ended in `ORDER BY id LIMIT 20`. At 10M rows this forces the planner to walk
`tickets_pkey` in order and probe `numbers` once per row through a Memoize node: 13.4 ms for `123***`
against 0.148 ms without the ordering, a 90× slowdown, and 54–92× across the other narrow classes.
Under 100 concurrent users the ordered form saturated the two-core database and every wildcard class
queued equally.

## Decision

Remove `ORDER BY` from `/v1/search`. Return whichever available matching tickets the index scan
reaches first, up to `LIMIT`. Keep an explicit `ORDER BY id` only on the small result set returned
by an allocation, where it is applied after the rows are chosen.

## Alternatives

- **Keep ordering and add a covering index** — the ordering itself, not the index, forces the walk.
- **Order in the API after fetching** — meaningless for a page of 20 drawn from a pool of a million.

## Consequences

Per-query time fell from tens of milliseconds to well under one; the planner is free to start from
the `numbers` table and stop after about two numbers. Search results have no stable order between
calls, which is acceptable because no requirement asked for one. Stable pagination, if ever needed,
is a separate design question.

## Evidence

`docs/explain-k8s-10M-orderby.txt` versus `docs/explain-k8s-10M.txt`; `docs/evidence/s1-C/` — p95
46.7 ms at 6,068 req/s with the ordering removed.
