# ADR-002: Resolve patterns on a 1M-row `numbers` table, then join (Strategy C)

Status: Accepted · Date: 2026-09-05 · Relates to: design doc Sections 5.3 and 6.2

## Context

A six-digit ticket has only 10⁶ possible values, so 10M tickets average ten per number. Wildcards may
appear in any position, which defeats an ordinary B-tree on the ticket number. Four indexing
strategies were built and measured on the same 10M-row dataset on PostgreSQL 17.11.

## Decision

Keep a static table `numbers(n, d1..d6)` of all one million values, indexed per digit. Resolve the
pattern there first — fixed leading digits collapse to a primary-key range, a fully specified pattern
skips the table entirely — then join into `tickets(number)` through a partial index on available
rows. Push `LIMIT` into the scan.

## Alternatives

- **Baseline `LIKE`** — full scan; 829 ms for an exact pattern, and 94 % of requests fail under
  100 concurrent users.
- **Strategy A, per-digit expression indexes on `tickets`** — each digit is only 10 % selective, so the
  planner uses one index and filters the rest: 130 ms per exact query, 405 MB of indexes, database
  throttled at up to 395 % of quota, 25 req/s.
- **Strategy B, dimension table without the prefix range** — correct but 1–5 ms per query and 975 req/s
  under load versus 6,068 for C.

## Consequences

201 MB of indexes, half of A. Search cost is bounded by the 1M-row table and a couple of probes, so it
does not grow with ticket count. The bottleneck moves to the stateless API, which can be replicated.
One extra join and one extra table to seed once.
