# ADR-008: Do not adopt Strategy D

Status: Accepted · Date: 2026-09-05 · Relates to: design doc §6.3

## Context

PostgreSQL 17 can satisfy `= ANY(array)` in a single B-tree descent. That makes a different query
shape viable: the API enumerates the matching numbers and sends them as an `int[]` instead of a
subquery against `numbers`. Applicable only to patterns with at most three wildcards (1,000 values,
about 4 KB). It was implemented as Strategy D and measured on both versions.

## Decision

Do not adopt it. Keep Strategy C as the single search path.

## Alternatives

- **Adopt D for narrow patterns** — measured faster: p95 39.1 vs 58.3 ms on 16, 33.7 vs 38.8 ms
  on 17, and it halves database CPU (37 % vs 72 %). Rejected for the reasons below.

## Consequences

D's benefit is database headroom, not user-visible speed: its throughput is identical on both versions
(6,051 and 6,047 req/s) because at 37 % database CPU it is bound by the API. The capacity model puts
the database at 39 % at 10,000 req/s, so more headroom solves a problem this system does not have.
Upgrading to 17 buys the same latency (C on 17: 38.8 ms; D on 16: 39.1 ms) without a second predicate
path, a per-request allocation of up to 1,000 integers, or 4 KB of extra traffic per narrow query.
Revisit if the database becomes the constraint: this measurement says D would then roughly halve its
CPU. The implementation remains in the code behind `STRATEGY=D` for that purpose.
