# ADR-008: Do not adopt Strategy D

Status: Accepted · Date: 2026-09-05 · Relates to: design doc Section 6.3

## Context

PostgreSQL 17 can satisfy `= ANY(array)` in a single B-tree descent. That makes a different query
shape viable: the API enumerates the matching numbers and sends them as an `int[]` instead of a
subquery against `numbers`. Applicable only to patterns with at most three wildcards (1,000 values,
about 4 KB). It was implemented as Strategy D and measured against C on the same dataset and pod
profile, with a script whose classes include `dd*d**` — the scattered-digit case where C has no key
range to exploit.

## Decision

Do not adopt it. Keep Strategy C as the single search path.

## Alternatives

- **Adopt D for narrow patterns** — measured: throughput 6,110 vs 4,856 req/s (+26 %) and database
  CPU 35 % vs 71 %, but p95 55.7 vs 48.4 ms (+15 %). Rejected for the reasons below.

## Consequences

D's benefit is database headroom, not user-visible speed: it halves database CPU by dropping the join
against `numbers`, while the API pod is the saturated resource in both runs and the latency tail does
not improve. The capacity model puts the database at 36 % at the illustrative 10,000 req/s target, so more headroom solves a
problem this system does not have, and D would add a second predicate path, a per-request allocation
of up to 1,000 integers, and 4 KB of extra traffic per narrow query. Revisit if the database becomes
the constraint: this measurement says D would then roughly halve its CPU. The implementation remains
in the proof of concept behind `STRATEGY=D` for that purpose.
