# ADR-001: Use a single PostgreSQL instance; no cache, no lock service

Status: Accepted · Date: 2026-09-05 · Relates to: design doc Section 6.1

## Context

The system must search 10M tickets by wildcard pattern and hand each matching ticket to at most one
of many concurrent users. The second requirement is the hard one: it needs an atomic, contention-safe
way to claim rows. The obvious reflex is to add Redis for caching or locking.

## Decision

Run one PostgreSQL instance holding `tickets`, the static `numbers` lookup table, and an append-only
`allocations` ledger. Claim tickets with `SELECT … FOR UPDATE SKIP LOCKED` inside the same statement
that updates the row and writes the ledger. Add no other stateful component.

## Alternatives

- **Redis cache in front** — creates a consistency problem exactly where correctness matters most;
  allocation must write to the database anyway, so the cache cannot own the decision.
- **Redis distributed lock** — lock expiry, dead-holder recovery, and still a database write.
  `SKIP LOCKED` gives the same guarantee transactionally.
- **Elasticsearch** — solves text search, not a fixed 10⁶ key space, and offers nothing for atomic
  allocation.

## Consequences

One component to deploy, back up and reason about; reservation and audit are one transaction. The
database becomes the single scaling limit beyond roughly 20,000 req/s, at which point read replicas
for search only are the next step. Total storage for 10M tickets and all indexes is about 1.4 GB.

## Evidence

`docs/evidence/s2b/30-verify.txt` — 246,782 allocations under 200-way contention, 0 duplicates.
`docs/evidence/c1-capacity/50-capacity.json` — 36 % database CPU projected at the illustrative 10,000 req/s target.
