# ADR-007: Deploy on PostgreSQL 17

Status: Accepted · Date: 2026-09-05 · Relates to: design doc Section 6.4

## Context

The proof of concept pins `postgres:17-alpine`, and every measurement in the design document was
taken on PostgreSQL 17.11: one dataset, one pod profile, one set of capture scripts. Nothing in the
design depends on a 17-only feature — `SKIP LOCKED`, partial B-tree indexes and the primary-key range
that Strategy C relies on all behave the same on 16 — so the question is whether to recommend the
version that was measured or leave it open.

## Decision

Recommend PostgreSQL 17 and treat it as part of the measured configuration. Every figure in the design
document has a single provenance, 17.11, and none is restated or scaled from another version.

## Alternatives

- **Leave the version unspecified** — every number in the document would then describe a
  configuration other than the one being proposed.
- **Recommend 16** — the schema and SQL run unchanged on it, but none of the figures were taken there,
  and 17's single-descent `= ANY(array)` scan is what made the Strategy D comparison (ADR-008) worth
  measuring in the first place.

## Consequences

Deployment uses the version that was load-tested. A later major-version upgrade is a version bump with
no schema or SQL change, but the suite (`make capture-all` in the proof of concept) should be re-run
rather than the figures assumed to carry over — a single-query benchmark and a concurrency benchmark
answer different questions, and only the latter is what the design rests on.

## Evidence

`pg_version=17.11` in every `docs/evidence/*/41-run.txt`; `deploy/k8s/03-postgres.yaml` in the
proof of concept pins the image.
