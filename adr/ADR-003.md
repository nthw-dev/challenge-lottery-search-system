# ADR-003: Guarantee duplicate-free allocation with `FOR UPDATE SKIP LOCKED` in one statement

Status: Accepted · Date: 2026-09-05 · Relates to: design doc §5.4

## Context

Many users may search the same pattern at the same instant and each must receive different tickets.
The guarantee has to hold across API replicas and survive process crashes mid-allocation.

## Decision

One SQL statement does everything: a CTE selects candidate rows with `FOR UPDATE SKIP LOCKED`, an
`UPDATE` marks them reserved, and an `INSERT` records the allocation in an append-only ledger. One
statement is one transaction, so the three steps either all happen or none do. `SKIP LOCKED` makes a
concurrent allocator step over rows another transaction holds rather than wait for them.

## Alternatives

- **`FOR UPDATE` without `SKIP LOCKED`** — correct but serializing; every allocator queues behind the
  first and latency reaches seconds under contention.
- **Optimistic locking with a version column** — retry rate climbs with contention on a popular
  pattern until throughput collapses.
- **Application-level lock** — cannot work across replicas, which is the primary scaling path.
- **Distributed lock in Redis** — see ADR-001.

## Consequences

No two users can receive the same ticket; nobody waits, so latency does not degrade with concurrency;
deadlock is impossible because no transaction waits on another. The ledger makes the guarantee
auditable with one `GROUP BY … HAVING count(*) > 1` query. Reservations need an expiry sweep, which
belongs in a scheduled job rather than the API process.

## Evidence

`docs/evidence/s2/30-verify.txt` and `s2b/30-verify.txt` — 351,481 allocations across two 200-VU
runs, 0 duplicates, 0 ledger/state mismatches. `docs/evidence/pg17-s2b/` — 265,344 more on
PostgreSQL 17, also 0. `internal/repository/repository_test.go` asserts the same invariant with 50
goroutines competing for 120 tickets.
