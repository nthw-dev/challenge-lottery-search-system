# ADR-004: Allocate by random concrete-number probe before falling back to a pattern scan

Status: Accepted · Date: 2026-09-05 · Relates to: design doc §5.4

## Context

The first allocation query took candidates in `id` order. Every reserved row stays at the front of
that order, so each new allocation walked past all previous ones. After only 713 reservations a
single allocate scanned 68,453 rows and took 145 ms, and it kept growing.

## Decision

Pick a random concrete number inside the pattern (`****23` → e.g. `481723`), do a point lookup on the
partial `tickets(number)` index with `SKIP LOCKED`, and retry up to three times before falling back to
the full pattern scan. Correctness still comes from `SKIP LOCKED` on both paths; the random probe is
purely a performance measure.

## Alternatives

- **Keep `ORDER BY id`** — cost grows with every allocation; rejected by measurement.
- **Pattern scan without ordering** — better, but every allocator still starts from the same rows and
  contends on them.
- **Track a per-pattern cursor** — shared mutable state across replicas, which ADR-001 avoids.

## Consequences

Concurrent users spread across 10^wildcards numbers, so collisions are rare and cost is constant
regardless of inventory consumed. When a pattern is nearly sold out the probes increasingly miss and
the fallback dominates: p95 rose from 74 ms to 548 ms at 96 % drained. That is a product decision
(withdraw a nearly-sold-out pattern), not a database problem, but it must be designed for.

## Evidence

`docs/evidence/s2b/` — 4,258 allocations/s at p95 73.8 ms while the pool is far from exhaustion;
`docs/evidence/s2/` — the same script on a pool that drained to 96 %, p95 548 ms.
