# ADR-006: Liveness must not touch the database; readiness must

Status: Accepted · Date: 2026-09-05 · Relates to: design doc Section 7.3

## Context

The first health endpoint pinged the database and served both probes. When Postgres saturated under
the baseline strategy, the liveness probe timed out and Kubernetes killed a healthy API pod, turning
a database slowdown into an API outage. A third of requests in that run failed for that reason.

## Decision

Split the probes. `/healthz` is liveness and answers from the process alone — it never opens a
database connection. `/readyz` is readiness and pings the database. Both carry explicit timeouts.

## Alternatives

- **One endpoint for both** — the failure mode above.
- **No readiness probe** — an overloaded pod keeps receiving traffic it cannot serve instead of being
  taken out of rotation.

## Consequences

A saturated database now degrades the service (the pod is removed from the load balancer until it
recovers) instead of restarting it. The baseline strategy's 94 % failure rate under load is the
readiness probe working correctly: the pod was pulled from the Service, and requests failed fast with
`EOF` rather than hanging.

## Evidence

`docs/evidence/s1-0/10-k6.log` — 15,592 of 16,528 requests failed, 15,588 with `EOF`, zero pod
restarts; cluster events show readiness probe timeouts and no liveness kills.
